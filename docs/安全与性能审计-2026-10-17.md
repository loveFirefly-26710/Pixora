# Pixora 安全与性能审计报告

- 审计日期：2026-10-17
- 项目版本：0.1.3
- 审计基线：`6abf614`（`master`）
- 审计范围：Rust 后端（HTTP 路由、鉴权、上传、存储、队列、安装向导）、前端关键渲染路径、部署配置
- 审计方式：源码逐项核查 + 现有测试 + 真实进程端到端冒烟 + 公开依赖审计

## 1. 结论摘要

这次审计确认并修复了 3 个高危问题、7 个中危问题，以及若干性能和纵深防御问题。最需要优先处理的三项是：

1. **用户上传的 SVG 没有走净化**。代码里有 `sanitize_svg`，但只用在站点背景/默认头像上；普通上传的 SVG 原样入库，直链只靠响应头 CSP 兜底。现在上传链路会在入库前净化，并重算哈希。
2. **OAuth `state` 只签名、没有绑定发起流程的浏览器**。攻击者可以把自己发起流程的 callback URL 发给受害者，形成 login CSRF。现在 `state` 的哈希存在 HttpOnly Cookie 里，回调必须对得上。
3. **确认弹窗把用户可控文本当 HTML 渲染**。相册名、图片标题、令牌名、设备名（User-Agent）都可能进入 `innerHTML`，构成存储型 XSS，且管理员查看用户内容时可能被打到。现在弹窗字符串按纯文本渲染，只保留 `<br>` 换行。

性能方面，最主要的变化是给设置读取加了 5 秒进程内缓存、把会话/令牌活动时间的写库节流到 60 秒一次、把随机图从全表 `ORDER BY RANDOM()` 换成主键区间随机起点，并把 Argon2 哈希移入受限的阻塞线程池。按当前代码结构，一次广场浏览不再产生几十次设置查询和几十次会话 UPDATE。

修复后：

- `cargo test --workspace` 全部通过。
- `cargo check --workspace --all-targets` 通过。
- `npm run typecheck`、`npm run build` 通过。
- 真实进程端到端冒烟 **299 项通过、0 失败**。
- `npm audit --omit=dev` 报告 0 个漏洞；`cargo audit` 当前环境未安装，未能执行。

## 4. 重点问题分析

### 4.1 SVG 上传未净化（SEC-01）

原实现里 `media::sanitize_svg` 只被 `admin::upload_site_asset` 调用；普通上传在嗅探到 `image/svg+xml` 后直接落盘。直链响应虽然有 `Content-Security-Policy: sandbox; script-src 'none'`，但这是第二道防线，不能替代入库净化：文件被下载、转到别的反代、或以后新增一种读取路径时，CSP 不一定跟着走。

修复内容：

- 在 `upload_file` 嗅探到 SVG 后调用 `Collected::sanitize_svg_in_place`，净化后重算大小、SHA-256、头部与尺寸元数据。
- 净化器保留 SVG 的大小写敏感标签/属性（`linearGradient`、`viewBox`），避免把合法图形改坏。
- 按本地名过滤 `svg:script` 这类带命名空间的标签；此前只比较完整标签名，换前缀即可绕过。
- 结束标签查找也按本地名匹配，避免 `<svg:script>` 后面的正常内容被整段丢掉。
- 直链与站点资产的 SVG CSP 加上 `default-src 'none'`、`img-src data:`、`frame-ancestors 'none'`。
- 新增集成测试：上传带 `<script>` 和 `onload` 的 SVG，取回后断言脚本、事件属性、脚本文本都不存在，正常 `<rect>` 保留。

### 4.2 OAuth state 未绑定浏览器（SEC-02）

`state` 的签名只证明“这张票是服务端签的”，不证明“callback 是同一个浏览器打开的”。攻击者可以自己发起一次 OAuth 流程，把 provider 回调 URL 发给受害者；受害者完成授权后，服务端把受害者登录进攻击者的账号。

修复内容：

- `/auth/oauth/{provider}/start` 把 `state` 的 SHA-256 写进 HttpOnly Cookie，`Path=/api/v1/auth/oauth`、`SameSite=Lax`、10 分钟有效。
- callback 必须同时满足签名有效、provider 一致、Cookie 里的哈希与本次 `state` 的哈希常量时间相等。
- 成功、失败、补邮箱、绑定各条路径都会清掉这个 Cookie。
- `redirect_uri` 改用 `state.base_url()`（设置优先），安装向导里写的站点地址现在会真正用于 OAuth 回调。
- `next` 的站内相对路径校验新增反斜杠与控制字符拒绝，覆盖 `/\evil.com` 这种浏览器会规范成 `//evil.com` 的写法。

### 4.3 确认弹窗的存储型 XSS（SEC-03）

`openModal` 对字符串 body 使用 `innerHTML`，`confirmDialog` 对字符串 message 也使用 `innerHTML`。这些字符串里包含：

- 相册名（用户可改）；
- 图片标题/原始文件名（用户可改）；
- API Token 名称（用户可改）；
- 设备名（来自 User-Agent，登录时可伪造）；
- 管理员填的 IP 备注、存储后端名称、条款版本等。

普通用户可以把恶意 HTML 放进相册名或图片标题；管理员在用户详情或回收站里执行删除/恢复时，脚本就在管理员会话里执行。由于 CSRF Token 存在非 HttpOnly Cookie 里，XSS 可以直接带着它调用管理接口。

修复内容：

- 弹窗字符串统一走 `textWithBreaks`：按纯文本创建文本节点，只把 `<br>` 识别为换行。
- 不再有调用点把用户输入拼进 `innerHTML`；`h(..., { html: ... })` 仅保留给静态 SVG、二维码和已经显式转义的列表。
- 重新构建了 `web/dist/main.js`，产物随本次提交更新。

### 4.4 API 限流未接线（SEC-04）

`RateLimits::check_api` 与 `record_api` 有实现、有单元测试，但没有任何路由调用它。管理界面里配置的“API 调用每分钟/每小时”实际上不生效，Token 客户端可以无限请求。

修复内容：

- 新增 `RateLimits::enforce_api`：读取用户生效的限流策略，走进程内令牌桶准入；Token 请求与写请求落库计数，浏览器读请求不记账（避免把每次看图变成两次写库）。
- `authenticate_optional` 对可选鉴权的读请求执行读额度；`require_user_allow_pending` 按 HTTP 方法区分读写，并只扣一次额度。
- 新增端到端测试：把全局读额度设为 1，同一个会话第二次 `GET /me` 返回 429。

注意：`api_per_hour` 与 `api_burst` 仍未接入；当前生效的是每分钟额度。多实例部署时进程内令牌桶各自独立，实际额度会按实例数放大。

### 4.5 IP 风控的覆盖面（SEC-05）

原来的 `ensure_ip_allowed` 只在注册、登录、上传、部分身份操作里调用。`scope=all` 的规则名为“全站”，但被拉黑的人仍可浏览广场、拉直链。另一个问题是 `Config::trust_proxy` 解析了环境变量却从未被读取，后台设置默认值才是实际生效的那份。

修复内容：

- `IpGuard` 接收 `PIXORA_TRUST_PROXY` 作为默认信任层数；后台设置没写过时用它，写过后台设置则以后台为准。
- 新增全站中间件 `enforce_ip`，在所有路由（含静态资源和直链）进入业务前检查 `scope=all` 规则。
- 规则命中计数按“同一规则每分钟最多记一次”节流；被拦客户端反复重试不会把封禁变成写放大。
- 策略读取失败时默认不信任转发头，避免“读不到设置就信任客户端伪造的 X-Forwarded-For”。
- `blobs/exists` 预检也补上上传场景的 IP 检查。

### 4.6 关闭广场后的随机图后门（SEC-06）

`/plaza` 在 `plaza_public=false` 时会拒绝匿名请求，`/random` 的注释也写着“一并关掉”，但代码只判断了 `authenticate_optional` 是否返回 `Err`。匿名请求返回的是 `Ok(None)`，不是错误，于是继续发图。现在 `Ok(None)` 明确返回 403。

### 4.7 双因素失败的风控（SEC-07）

密码校验失败会记 IP 失败并触发自动封禁，但 TOTP 不匹配、邮箱验证码错误、恢复码错误只写了审计日志，没有计入 IP 风控。拿到密码的人可以把 6 位 TOTP 当成无限次数的在线爆破目标。现在这些失败都会走 `register_ip_failure`，达到阈值后按原有策略临时封 IP。

### 4.8 上传临时文件与 GC 竞态（SEC-10、SEC-11）

- `ReceiveFile` 与 `TempUpload` 原来用“当前微秒 + 进程 id”命名。同一进程并发上传完全可能撞名，两个请求会写到同一个临时文件。现在都补了 8 字节随机后缀。
- 本地存储的 `.part` 临时文件原来固定在目标路径旁，同一内容并发写入也会互相覆盖。现在使用 `pid + 原子序号` 的唯一临时名。
- 上传去重与 GC 之间原来存在“复查 ref_count → 删物理文件 → 删数据库行”的窗口，新上传可能在窗口内把引用挂到即将被删的实体上。现在按 SHA-256 首字节分 256 把锁：上传从查重到建图片引用持有对应锁，GC 从复查到删除持有同一把锁。锁是进程内的，多实例部署仍需要数据库级锁或只让一个实例跑 GC。

## 5. 性能审查

### 5.1 设置读取缓存（PERF-01）

`Settings::raw` 每次直接查 `settings` 表。`site()` 一次读 8～9 个键，`hotlink()` 读 3 个，`IpGuard::policy()` 读 6 个；直链请求、每次鉴权、每次上传都会走这些路径。按一次广场浏览几十张图估算，设置查询量会到数百次。

现在 `Settings` 带 5 秒 TTL 的进程内缓存，按 key 缓存，连“键不存在”也缓存；`set`/`set_secret` 写入后立即删除对应键。多实例部署最多延迟 5 秒看到别的实例的修改。

### 5.2 会话活动时间节流（PERF-02）

直链图片也会走 `authenticate_session`，原实现每个请求都 `UPDATE sessions SET last_seen_at`。一次相册浏览就是几十条写。现在只有在 `last_seen_at` 超过 60 秒或 IP 变化时才写；API Token 的 `last_used_at` 同样节流。闲置超时以分钟计，60 秒粒度不影响判定。

### 5.3 随机图快路径（PERF-03）

`/random` 原来对公开图做 `ORDER BY RANDOM() LIMIT 1`，数据量大时要全表扫描并排序；首页/博客头图这类场景可能被高频调用。现在无搜索、无标签、无用户的公开随机图走主键区间随机起点：

1. 取公开图的 `MIN(id)` / `MAX(id)`；
2. 在区间里随机取一个 id；
3. 找第一张 `id >= 目标` 的公开图，没有就回绕到第一张。

带搜索、标签、用户的随机图仍保留原语义。广场的“随机排序”是另一种稳定 seed 的模运算排序，仍然会对全量候选排序；大库上建议改用随机起点或分页缓存。

### 5.4 Argon2 并发（PERF-04）

Argon2id 参数是 19 MiB、2 次迭代、并行度 1。原实现直接在 async handler 里同步调用 `hash_password` / `verify_password`，会占住 tokio worker；并发登录也没有上限，容器内存限制 128M 时几份哈希就会逼近上限。

现在 `AppState::hash_password` / `verify_password` 通过 2 个许可的信号量限流，实际计算放在 `spawn_blocking`。注册、登录、改密、重置、管理员建号/改密、安装向导都改走这一对方法。

### 5.5 远端存储上传的内存（PERF-05）

远端后端（GitHub/Telegram 等）需要整份内容，`store_object` 会把上传流读成 `Vec<u8>`，原实现还 `clone()` 一份给第一次写入，峰值是两倍文件大小。现在改成 `Arc<[u8]>` 共享，第一次和失败回退共用同一份，减少一次完整拷贝。代价是仍然要把整份文件放在内存里；默认 20 MiB 单文件 + 并发上传时，128M 容器会比较紧。

### 5.6 缩略图兜底与启动扫描（PERF-06）

`refresh_small_thumbs` 会在启动任务里无条件跑，即使 `thumb_server_fallback` 关闭。它会解码旧图并重新编码，和“服务端默认不缩放”的约束冲突，也可能在 128M 容器里触发 OOM。现在该函数先检查 `thumb_server_fallback`，关闭时直接返回；管理员显式点“重算缩略图”仍会走 `regenerate_batch`。

## 8. 仍未修复或需要部署侧决定

1. **多实例的 GC 与限流**：blob 锁、会话节流、进程内令牌桶都只作用于单个进程。多副本 + 共享 PostgreSQL/MySQL 时，需要数据库 advisory lock 或单独的 GC 实例；否则两个实例可能同时回收同一实体。
2. **服务条款未被服务端强制**：前端登录后会弹条款，但 API Token 可以绕过；注册流程也没有落一条同意记录。若条款具有法律约束力，建议在 `require_user` 里对未同意当前版本的账号返回明确的 `TERMS_REQUIRED`，并在注册请求里带上同意标记。
3. **API 小时额度与 burst**：`api_per_hour`、`api_burst` 仍未接入，只有每分钟额度生效。
4. **登录计时的用户枚举**：账号不存在时跳过 Argon2，响应会比密码错误快。IP 自动封禁降低了撞库价值，但没有完全消除时序差异。
5. **广场随机排序的成本**：稳定 seed 的模运算排序仍会对候选集全量排序；`/plaza` 每次还要做 `COUNT(*)` 与标签查询。大库上建议按随机起点取页或缓存热度页。
6. **远端存储整份缓冲**：为了失败回退，仍然把文件读入内存；20 MiB × 并发数 + Argon2 19 MiB × 2 在 128M 容器里余量不大。
7. **服务端缩略图解码上限**：60MP 解码峰值约 240 MB，超过 128M 限制。开启兜底前先调高容器内存，或把上限降到 10–20MP。
8. **历史 SVG**：本次只保证新上传的 SVG 净化；修复前已入库的 SVG 仍按原字节服务。直链 CSP 会拦住脚本，但建议做一次批量重写/清理。
9. **Docker root**：镜像仍是 root 运行；改成非 root 需要同时调整 `./data` 属主，属于部署变更，本次没有动。
10. **`cargo audit`**：环境没有安装 `cargo-audit`，本次只完成了 `npm audit`。上线前建议在 CI 加 `cargo audit` / `cargo deny`。
