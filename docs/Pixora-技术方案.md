# Pixora 技术方案

> 一个面向高并发、低内存占用的多用户图床系统
> 版本 1.0 · 设计冻结稿

---

## 1. 项目定位

Pixora 是一个自托管的图片托管服务。它同时服务两类人：一类是想把图片丢进去、拿一条干净的直链就走的人；另一类是需要在团队或社区里按人、按相册把图片管起来的管理员。

它要解决的问题很具体。市面上多数图床在单机 Docker 里跑起来，光运行时内存就吃掉几百兆，再挂个数据库就顶到 1GB 以上；上传是即选即传，选中 1000 张图浏览器会同时开 1000 条连接把服务器打满；缩略图由服务端用 GD/ImageMagick 生成，CPU 直接成为瓶颈；同一张图被两个用户上传，磁盘上就存两份，删一份还容易误伤另一份。

Pixora 的做法是：把缩略图和哈希计算推到浏览器，服务端只做校验、去重登记和落盘；用内容寻址的存储加上引用计数，让物理文件全局唯一、删除互不影响；用一条可控的队列把上传流量削峰；整套东西编译成一个 Rust 静态二进制（musl 目标，可跑在 scratch 镜像上），Docker 整栈内存按 500MB 预算，常规运行时按 200MB 以内估算。

## 2. 设计目标与约束

| 项 | 目标 |
|---|---|
| Docker 整栈满载内存 | ≤ 500MB |
| 常规运行时内存 | 越低越好，目标 150–250MB |
| 单次上传规模 | 一次选中 1000 张图，稳定排队完成 |
| 存储后端 | 本地磁盘（默认）、数据库、GitHub、WebDAV、Telegram，可扩展 |
| 元数据库 | PostgreSQL（默认）、MySQL/MariaDB、SQLite |
| 部署形态 | 单机 Docker Compose，一条命令起 |
| 前端能力 | 缩略图生成、哈希计算、批量排队全在客户端完成 |
| 直链 | 隐藏真实目录与文件名，形如 `https://域名/images/hash.png` |
| 多端 | PC 与移动端同一套代码，五个断点自适应 |
| 账号治理 | 邮箱验证、暂停与封禁、频率限制、IP 黑白名单 |
| 条款合规 | 服务条款版本化，首次登录强制通告并留同意记录 |

约束写死两条：服务端不承担图像缩放；服务端不承担大文件哈希（仅作为 API 上传的兜底）。

## 3. 技术选型

### 3.1 语言与运行时

先给结论：**Rust**。不选 Go 不是 Go 不行，而是内存和性能这两项都要最好、工期又不计入考量，那 Rust 就没有对手。

| 方案 | 空载常驻内存 | 负载下峰值 | 并发模型 | 尾延迟 | 判断 |
|---|---|---|---|---|---|
| **Rust + axum / tokio** | 3–10MB | 20–60MB | 异步，无 GC | 稳定，无停顿 | **首选** |
| Go 1.23 | 10–20MB | 40–150MB | goroutine，有 GC | 受 GC 影响 | 备选 |
| Java / JVM | 150–300MB+ | 更高 | 线程池 | 受 GC 影响大 | 排除 |
| Python | 60–120MB/worker | 更高 | GIL 限制 CPU | — | 排除 |
| Node.js | 80–150MB | 更高 | 单线程事件循环 | 大文件哈希阻塞主线程 | 排除 |

差距落在两个地方。

**内存**上，Rust 没有运行时和 GC，进程常驻内存就是代码段加少量堆，5MB 上下是常态。Go 要带上 runtime、GC 元数据和 goroutine 栈，空载就 10–20MB 起步，压力上来后堆还会跟着涨，峰值能到 Rust 的两三倍。

**性能**上，这个负载是 I/O 密集（读写小文件、转发网络请求），两者的吞吐差距没有想象中大。真正拉开距离的是尾延迟：Go 的 GC 在高负载下会产生毫秒级停顿，Rust 没有，P99 更可预测。对图床这种请求量集中、用户对卡顿敏感的服务，尾延迟比平均吞吐更值钱。

图床还有个特性对 Rust 有利：几乎没有 CPU 密集计算（缩放和哈希都推给浏览器了），所以不需要 GC 来"自动管理复杂对象图"。Rust 的所有权模型在这个场景里不是负担，是直接的红利。

代价也说清楚。全量编译要几分钟，增量编译也慢；异步 Rust 的心智负担不低（生命周期、`Send`/`Sync` 边界、`Pin`）；成熟库比 Go 少一档，选型时要多花时间验证。既然工期不计入，这些都可以接受。

一条补充建议：**换掉默认分配器**。glibc 的 malloc 在长时间运行的服务里容易碎片化，换成 `mimalloc` 能把常驻内存再压一截，对图床这种频繁申请释放缓冲区的服务尤其明显。

构建配置也要调：`opt-level = 3`、`lto = "fat"`、`codegen-units = 1`、`panic = "abort"`，能同时减小二进制体积、提升运行性能。代价是编译更慢，反正工期不计入。

### 3.2 依赖选型

| 用途 | crate | 说明 |
|---|---|---|
| HTTP 服务 | `axum` + `tokio` | 生态最成熟，`tower` 中间件可组合 |
| TLS | `rustls` | 纯 Rust，免 OpenSSL 动态库，静态编译干净 |
| 数据库 | `sqlx`（PostgreSQL / MySQL）、`rusqlite`（SQLite） | sqlx 编译期校验 SQL；rusqlite 开 bundled 特性自带 SQLite 源码，免系统依赖 |
| 图像元数据 | `image` | 只读尺寸和格式校验，不做缩放 |
| 哈希 | `sha2` | SHA-256 |
| 密码 | `argon2` | Argon2id |
| 加密 | `aes-gcm` | 存储后端凭据加密 |
| 邮件 | `lettre` | SMTP，支持 STARTTLS / SSL |
| 限流 | `governor` | 令牌桶 |
| 分配器 | `mimalloc` | 降低碎片与常驻内存 |
| 序列化 | `serde` + `serde_json` | |
| 静态资源 | `rust-embed` | 前端构建产物打进二进制 |

不引入的东西也说明一下：不用 Redis（进程内队列够用），不用 ORM（sqlx 直接写 SQL 更可控），不用 ImageMagick 或任何图像处理库做缩放（服务端不碰像素）。

### 3.3 架构风格

按照 Richards 和 Ford 在《软件架构基础》里的框架，先明确这个系统**真正需要**的架构特性，而不是把所有 -ility 都写进需求——那是典型的"子弹打满的尸体"反模式。Pixora 只要五个特性，按优先级排：

1. **性能**（吞吐与延迟）
2. **可伸缩性**（单机内垂直扩展 + 无状态水平扩展）
3. **容错性**（单个存储后端故障自动回退，不影响主流程）
4. **可部署性**（一条命令起，无外部强依赖）
5. **简单性**（一个人能看懂、能维护）

按这个标准筛选架构风格：

| 风格 | 成本 | 简单性 | 可伸缩性 | 容错性 | 适配度 |
|---|---|---|---|---|---|
| 分层架构 | 高 | 高 | 低 | 低 | 作为**内部**结构合适，作为整体不够 |
| 微内核 | 中 | 中 | 中 | 高 | **存储驱动层**用这个，插件化后端 |
| 基于服务 | 中 | 中 | 中 | 高 | 可拆分，但会抬高内存与运维成本 |
| 微服务 | 低 | 低 | 高 | 高 | 排除，500MB 预算下自相矛盾 |
| 空间架构 | 低 | 低 | 高 | 高 | 排除，内存数据网格与低内存目标冲突 |

**最终选型：模块化单体（Modular Monolith），内部采用分层结构，存储后端采用微内核插件模式。**

理由很直白。微服务的最大代价是运维复杂度和资源开销，而这两个恰好是本项目的硬约束。图床的业务边界清晰、耦合度低，一个进程内的模块化单体完全能撑住，还能省下进程间通信和重复的运行时开销。内部按层组织（HTTP 层、服务层、仓储层、存储驱动层），但每层内部按业务域切成独立包，边界靠接口约束，将来真要拆服务，改动是可控的。

存储后端则天然适合微内核：核心系统只认识 `StorageDriver` 接口，本地磁盘、数据库、GitHub、WebDAV、Telegram 各自是一个插件。新增一种后端等于新增一个实现，核心代码不动。这跟原书对微内核的描述一致——核心系统负责通用逻辑，插件提供变化点。

这个决策建议落成一份 ADR，附录里给了模板。

### 3.4 内存预算

单机 Docker Compose 整栈拆解如下（PostgreSQL 方案）：

| 组件 | 常驻目标 | 峰值 | 关键手段 |
|---|---|---|---|
| Pixora 应用（API + Worker 同进程） | 12–30MB | 60MB | mimalloc、tokio 工作线程可配、流式读写不整文件载入 |
| Caddy 反向代理 | 15–25MB | 35MB | 承担 TLS、静态资源、直链缓存 |
| PostgreSQL 16 | 96–140MB | 200MB | shared_buffers=64MB、work_mem=4MB、max_connections=50 |
| 系统与容器开销 | 20–30MB | 40MB | scratch / alpine 基础镜像 |
| **合计** | **~145–225MB** | **~335MB** | 距 500MB 上限留出约 33% 余量 |

按同样的估算，换成 **SQLite** 方案可以把整栈预算压到 **80MB 以内**：应用 12–30MB + Caddy 15–25MB，没有独立数据库进程。单文件数据库、零运维、备份就是拷一个文件。代价是写并发受限（WAL 模式下够用），以及多实例部署时不能共享。

表中的数字是设计预算，不是压测结果。项目目前没有做过 Docker 整栈的内存实测；这些数只能说明大致量级，实际占用取决于并发连接、单文件大小、是否开启服务端缩略图兜底，以及反向代理和数据库的配置。按这个口径：

- 单机、个人或小团队 → **SQLite 默认**，这是内存最优解。
- 需要多实例、或有并发写入压力 → **PostgreSQL**。

作为量级参考，2026-10-19 在一台 Windows 11 x64 开发机上用 release 构建、SQLite 和全新数据目录跑过一次：空载工作集 13.2MB；以 50 并发请求 2000 次 `/api/v1/site` 后，工作集 23.3MB。这个数字不包含 Caddy，也不代表 Linux 容器，不能当作整栈实测结果。

方案默认 PostgreSQL（按需求指定），但把 SQLite 作为"极致省内存"的推荐项一并提供。

### 4.1 分层与模块

```
┌─────────────────────────────────────────────────────┐
│  Caddy  (TLS / 静态资源 / 直链缓存 / 限流)              │

                           │
┌──────────────────────────▼──────────────────────────┐
│  Pixora 单二进制                                      │
│                                                       │

│  │  路由 / 中间件(鉴权·CSRF·限流·日志) / 参数校验   │   │
│  └───────────────────────┬───────────────────────┘   │
│  ┌── 应用服务层 ──────────▼───────────────────────┐   │
│  │  用户服务 · 相册服务 · 图片服务 · 广场服务       │   │
│  │  上传服务 · 配额服务 · 通知服务(邮件)            │   │

│  └───────────────────────┬───────────────────────┘   │
│  ┌── 基础设施层 ─────────▼───────────────────────┐   │
│  │  存储驱动注册表(微内核) · 任务队列 · 邮件客户端   │   │
│  │  CAS 内容寻址存储 · 哈希 · 加密 · 审计           │   │
│  └───────────────────────────────────────────────┘   │
└───────────┬───────────────────────────┬──────────────┘
            │                           │
      ┌─────▼─────┐              ┌──────▼──────┐
      │ PostgreSQL│              │ 本地磁盘/CAS │
      │ /SQLite   │              │ /数据库BLOB  │
      │ /MySQL    │              │ /远端后端    │
      └───────────┘              └─────────────┘
```

几个刻意的设计点：

- **API 与 Worker 同进程**。后台任务（远端后端推送、缩略图兜底、Blob 垃圾回收与删除后即时催收、邮件重试）跑在进程内的有界异步任务池里，不引入 Redis 或独立 worker 容器。少一个进程就少一份内存和一套运维。
- **前端构建产物用 `rust-embed` 打进二进制**。部署时只有一个文件，不用挂载静态目录。
- **仓储层用 trait 隔离 SQL 方言**。PostgreSQL 和 MySQL 走 `sqlx`，SQLite 走 `rusqlite`（bundled 特性自带 SQLite 源码，免系统依赖，静态编译友好）。上层服务只调仓储 trait，不写方言 SQL。

### 4.2 存储驱动（微内核）

核心系统只依赖这个 trait：

```rust
#[async_trait]
pub trait StorageDriver: Send + Sync {
    fn name(&self) -> &'static str;

    async fn put(
        &self,
        key: &str,
        reader: Box<dyn AsyncRead + Send + Unpin>,
        size: u64,
        mime: &str,
    ) -> Result<StoredObject>;

    async fn get(&self, key: &str) -> Result<Box<dyn AsyncRead + Send + Unpin>>;
    async fn delete(&self, key: &str) -> Result<()>;
    async fn stat(&self, key: &str) -> Result<ObjectInfo>;

    /// 是否支持硬链接、是否可探测容量、是否支持流式读写
    fn capabilities(&self) -> Capabilities;
}
```

已实现的驱动：

| 驱动 | 说明 | 备注 |
|---|---|---|
| `local` | 本地目录，默认 | 支持硬链接去重镜像 |
| `database` | 存进数据库 BLOB/bytea | 适合小图或不想碰文件系统的场景 |
| `github` | Contents API 推送到仓库 | 需 Token |
| `webdav` | WebDAV PUT | Basic Auth |
| `telegram` | Bot API 发到频道 | 通过代理访问 |
| `s3` | S3 兼容对象存储（含阿里云 OSS、MinIO） | 可选，扩展位 |

`Capabilities()` 是关键。本地文件系统支持硬链接、能探测容量；对象存储两者都不支持。上层据此决定去重镜像策略和容量展示策略，不用写 `if driver == "local"` 这种硬编码判断。

## 5. 数据模型

### 5.1 核心实体

```
users ──┬── albums ──┬── images ──── blobs（内容寻址，全局唯一）
        │            │     └── tags[]
        │            └── upload_jobs
        ├── api_tokens          用户身份与访问
        ├── sessions            活跃会话，暂停时批量吊销
        ├── user_actions        处置记录：暂停/封禁/解封/改配额
        ├── rate_limit_policies 频率限制，user_id 为空即全局默认
        ├── terms_consents ──── terms_versions（条款版本化）
        └── quota_bytes/used_bytes

全局配置类
  settings             容量模式、默认配额、自动关闭注册阈值
  storage_backends     各存储后端实例与凭据
  ip_rules             IP 黑白名单，含风控自动加的临时规则
  email_templates      通知邮件模板
  disposable_domains   一次性邮箱域名清单
  audit_logs           操作与安全事件日志
```

**软删只是打标记，不构成引用，但保留期内钉住物理文件。** 回收站的保留期到了之后，墓碑由清理任务摘掉、文件由 GC 收走；回收站关着（保留 0 天）时两者都是立即的。 删除图片是给 `images.deleted_at` 写时间戳，`ref_count` 按「活着的引用」算；回收时连指向同一实体的墓碑行一起清掉——否则外键会把物理文件永远钉在磁盘上（没有回收站功能，内容没了，行也没有留的意义）。

**blobs 与 images 分离是去重的核心。** 一张物理文件在 `blobs` 里只有一行，`sha256` 唯一。任何用户、任何相册引用它，都在 `images` 里生成一行指向 `blob_id`。`blobs.ref_count` 记录被引用次数，删除图片时递减，归零才真正删物理文件。这样用户 A 删掉自己那张图，用户 B 的同一张图毫发无损。

处置、限流、条款这些都不往 `users` 表上堆字段，各自独立成表。原因是它们都需要留档：谁在什么时候因为什么被暂停、某个用户这个月被限流了几次、当初同意的是哪一版条款。塞进 users 表就只能存最新状态，历史全丢。

字段级设计见 `docs/schema.sql`，这里只说几个关键点：

- `users.uid`：短数字或短字符串，作为物理目录的一级分类。对外可见，但不含身份信息。
- `users.status`：`pending` / `active` / `suspended` / `banned`，鉴权中间件统一校验。
- `images.tags`：PostgreSQL 用 `text[]` + GIN 索引，MySQL 用关联表。两种实现藏在仓储层后面。
- `images.visibility`：`public` / `private`，广场只捞 `public`。
- `blobs.storage_driver` + `blobs.storage_key`：物理位置。CAS 布局是 `blobs/{sha256前2位}/{sha256}.{ext}`。
- `upload_jobs`：队列表，PostgreSQL 用 `FOR UPDATE SKIP LOCKED` 做无锁并发取任务，SQLite/MySQL 用等价的悲观锁写法。
- `rate_limit_policies`：`user_id` 为空的那行是全局默认，唯一索引保证只有一行。
- `terms_consents`：同意记录只增不改，且冗余存一份版本号，条款删除也能追溯。

### 5.2 物理目录布局

需求要求"目录按用户 UID 分类后再按相册分类"，同时要求"相同文件不重复占用空间"。这两条表面上冲突，用一个技巧化解：**CAS 存实体 + 硬链接做视图**。

```
{data_root}/
├── blobs/                     # 唯一真身，内容寻址
│   ├── a3/
│   │   └── a3f9c1...e7.webp
│   └── 7b/
│       └── 7b21d0...44.jpg
└── users/                     # 人类可浏览的镜像树（硬链接）
    ├── 1001/
    │   ├── 旅行/
    │   │   └── a3f9c1...e7.webp   ← 硬链接到 blobs/a3/...
    │   └── 工作/
    └── 1002/
        └── 头像/
            └── a3f9c1...e7.webp   ← 同一个 inode，磁盘只占一份
```

硬链接让同一份数据在多个路径下可见，但磁盘占用只算一次。用户在文件管理器里按 `用户/相册` 翻目录是直观的，`du` 统计也不会重复计算。

文件系统不支持硬链接时（部分 OSS/FUSE 挂载、Windows 部分场景），驱动降级为"只维护 CAS 实体 + 数据库虚拟目录树"，递归查询接口照常工作，只是磁盘上没有那棵镜像树。这个降级由 `Capabilities()` 自动决定。

## 6. 核心流程

### 6.1 上传：客户端哈希预检 + 排队

这是整份方案里最能省资源的一环。传统流程是"上传 → 服务端算哈希 → 发现重复 → 丢弃"，带宽和 CPU 都已经浪费了。Pixora 把顺序倒过来：

```
浏览器选中 1000 张图
   │
   ├─ 1. Web Worker 里逐张算 SHA-256（crypto.subtle.digest，不阻塞 UI）
   ├─ 2. 批量 POST /api/v1/blobs/exists  { hashes: [...] }
   │      服务端回 { exist: [...], missing: [...] }
   ├─ 3. 对 missing 的图片生成缩略图（OffscreenCanvas → WebP）
   ├─ 4. 只把 missing 的图片排进上传队列
   │      队列默认并发 1，逐张上传，带重试与退避
   ├─ 5. 每张上传成功后，为 exist + 新上传的图片统一建引用
   └─ 6. 全程进度持久化到 IndexedDB，刷新页面不丢队列
```

好处有三层。1000 张图里有重复的，根本不发出去，省带宽。服务端收到的都是新文件，不用做"算哈希再丢弃"的无用功。队列逐张发，服务器不会同时被 1000 条连接压垮。

客户端算 SHA-256 用的是浏览器原生 Web Crypto，对大文件用分片流式读取，不会把整个文件读进内存。缩略图用 `createImageBitmap` + `OffscreenCanvas` 在 Worker 里生成，同样不占主线程。

**API 上传（PicGo/PicList）没有客户端哈希这一步**，服务端就在流式接收时边收边算（`AsyncRead` 上挂一个 tee 写入器把字节同时喂给 `sha2`），收完立刻判断是否已存在。存在就丢弃临时文件、直接建引用；不存在就落盘。全程不把文件读进内存。

**格式校验和 SVG 净化也在这一条链路上。** 服务端只信魔数嗅探的结果，扩展名与真实格式不符时按真实格式处理；SVG 会在写库前走一次净化，去掉 `<script>`、事件属性、外部引用和带命名空间前缀的脚本标签，净化后重算哈希。缩略图同样要过魔数、体积和像素上限，4 MiB 的 PNG 可以解出很大的画布，不能因为“只是缩略图”就跳过检查。原始文件名会去掉路径和控制字符，截到 255 字符以内。

**远端驱动是例外。** GitHub、Telegram 这类后端需要整份内容，失败回退本地时也要重放一次，所以写入阶段会把文件读进内存；本地与数据库驱动仍然是流式。默认 20 MiB 单文件在 128M 容器里可以跑，但同时开多个远端上传、或同时做 Argon2 校验时余量不大，部署时按 §11 的说明放大内存或调小单文件上限。

### 6.2 队列与背压

客户端排队解决了"一次选 1000 张"的问题，但服务器还得防住恶意的或并发的 API 请求。

- **服务端有界队列**：`upload_jobs` 表是持久化队列，进程内有 N 个 worker（默认等于 tokio 工作线程数，可配）通过 `SKIP LOCKED` 取任务。
- **准入控制**：队列深度超过阈值时，新请求返回 `429` + `Retry-After`。客户端收到后指数退避重试。
- **每用户令牌桶**：限制单用户瞬时提交速率，防止一个账号打满队列。
- **任务可恢复**：进程重启后未完成的任务从队列表恢复，不会丢。

### 6.3 缩略图：默认客户端生成，服务端兜底可选

缩略图默认由客户端生成，随原图一起上传（multipart 里带 `thumb` 字段）。服务端只校验、存储，不碰像素；校验包括魔数、体积、像素上限与尺寸，缩略图本身也不能是解压炸弹。

API 上传（PicGo）通常不带缩略图。对此服务端**默认不生成**，列表页直接用原图加 `width/height` 属性让浏览器按容器缩放，配合 `loading="lazy"` 和 `decoding="async"`，实际带宽影响有限。管理员可以开启“缩略图兜底队列”，让低优先级的 worker 异步补生成，不阻塞上传主链路。这个开关关闭时，启动任务也不会偷偷扫描并重算旧图；管理员显式点“重算缩略图”才会进入分批重算。

服务端解码要放在 `spawn_blocking` 里，单张源图有体积与像素上限。容器内存只有 128M 时，开启兜底前先确认上限和实际内存匹配；60MP 的图解码峰值可以到两百多 MB。

### 6.4 直链：隐藏真实路径

复制出来的链接只有一级目录，不含用户 UID、相册名和原始文件名：

```
https://img.example.com/images/a3f9c1b8...e7.webp
                       └─ 一级目录，可配置，默认 images
```

文件名是内容哈希，天然不可猜测、天然唯一、天然不会泄露原始文件名。后端路由 `/{prefix}/{hash}.{ext}` 反查 `blobs` 表拿到物理位置，再由对应驱动返回内容。本地驱动可以直接由 Caddy 走 `X-Accel-Redirect` 或 `sendfile` 交给内核零拷贝发送，Rust 进程不参与数据传输。

一级目录名可在后台改（`images`、`i`、`p` 都行），改完旧的直链依然有效——因为映射关系在数据库里，不在 URL 结构里。

响应头按内容与访问者分开：公开图片 `Cache-Control: public, max-age=31536000, immutable`，私有图片 `private, max-age=300`；两者都带 `ETag` 与 `X-Content-Type-Options: nosniff`。SVG 额外带沙箱 CSP（禁止脚本、对象、远程资源，只允许 `data:` 内联图片）。应用层还会统一加 `X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy` 与 `frame-ancestors 'self'`，允许扫码登录的同源 iframe，同时挡住外部站点嵌套。

### 6.5 磁盘容量展示

这是必须修掉的一个坑：存储目录挂在 OSS 或网络盘上时，`statfs` 拿到的是挂载点所在宿主机的容量，跟真实可用空间没关系，展示出来就是错的。

处理方式是把容量展示拆成三种模式，管理员选：

| 模式 | 行为 |
|---|---|
| `auto` | 探测文件系统类型。识别为网络/对象存储挂载（FUSE、nfs、cifs、ossfs 等）时自动降级，不展示容量 |
| `manual` | 管理员手动填总容量，已用量 = 该存储驱动下所有 blob 的 `size` 之和，实时计算 |
| `hidden` | 完全不展示磁盘容量，界面上不出现这一项 |

探测逻辑读 `statfs` 的 `f_type` 字段对照已知网络文件系统类型表；同时在后台给一个"存储后端类型"的下拉，管理员可以手动指定，覆盖自动探测。两条路都堵死误判。

**两个"已用"口径要分开看。** 页面上出现的已用数字有两个来源，别混：

- **宿主机整盘已用**（总额 − 可用，`host_used`）：自动模式下的占用率与"容量触顶自动关闭注册"按它算。理由是磁盘满没满跟是谁占的无关——宿主机上与本项目无关的数据同样能把盘写满，只盯着本项目那点字节会漏判。界面上单列一行，注明"整盘，含本项目与其它占用"。
- **本项目占用**（`used`，库内 blob 汇总）：配额那条线的口径，也是手填总额或网络挂载降级时的占用率分子——手填的数可能只是给本项目定的预算，拿整盘占用去比它算不出有意义的百分比。

数字来源只有两处，不猜也不累加：整盘的已用与可用由文件系统给出（Linux 的 `statfs`、Windows 的 Win32 API），本项目占用由库内 blob 汇总。同一次探测里"已用 + 可用 = 总额"必然成立，不会出现两套对不上的数字。

### 6.6 配额：用户只看自己那份

`users.quota_bytes` 由管理员配置。普通用户在任何界面看到的都是"已用 X / 配额 Y"，Y 是管理员分配的额度，跟真实磁盘容量无关。

管理员在用户管理页给每人设额度，支持批量设置和默认额度。同一页还能直接建号（邮箱即时可用，密码由管理员转交）与把普通用户提为管理员；角色改动只由管理员发起，且不允许改自己的角色、不允许降级最后一个管理员。上传时服务端校验 `used_bytes + incoming <= quota_bytes`，超了就拒绝并在队列里标记该文件失败，其余文件继续。

`used_bytes` 的维护用引用计数的方式：图片建立引用时累加，删除时递减。定期（每小时）有一次对账任务用 `SUM(blobs.size)` 重算，修正可能的漂移。

## 7. 功能规格

按需求逐条落地。这里给的是设计结论，不是待办清单。

### 7.1 用户与登录

多用户体系，区分 `admin` 与 `user` 两种角色。注册走**邮箱验证**，不是填完用户名密码就能用。

流程：填邮箱和密码 → 服务端校验邮箱合法性 → 发验证邮件（6 位验证码或魔法链接，10 分钟有效）→ 用户验证通过后账号激活。未验证的账号无法登录。

邮件通道走 **SMTP**，默认预置阿里云企业邮箱参数（`smtp.qiye.aliyun.com:465`，SSL），也支持任意标准 SMTP。敏感凭据（SMTP 密码、存储后端 Token）用 AES-256-GCM 加密后存库，主密钥从环境变量或密钥文件加载，不进代码仓库。

**临时邮箱拦截**是三层的：

1. 内置一次性邮箱域名清单（随镜像打包，可在线更新），命中直接拒绝。
2. MX/A 记录校验，域名解析不出邮件服务器的一律拒绝。
3. 可选的第三方校验 API（如 Kickbox、Verifalia），管理员配置密钥后启用。

再加两条防绕过规则：拒绝明显的别名花样（Gmail 的 `+` 后缀和点号变体做归一化后判重）；同 IP、同邮箱的验证码发送做频率限制（如 5 次/小时）。

**登录防护**：密码用 Argon2id 哈希；连续失败 N 次锁定该账号一段时间；管理员账号强制或强烈建议开启 TOTP 二次验证（开启时给出二维码，由前端本地绘制，密钥不出浏览器）；会话用 HttpOnly + SameSite=Lax + Secure 的 Cookie，或 API 场景用签名 Token；所有写操作带 CSRF Token。

**账号状态**四种：`pending`（邮箱未验证）、`active`（正常）、`suspended`（暂停）、`banned`（封禁）。只有 `active` 能登录和调用 API。判断放在鉴权中间件里统一做，不散落到各个 handler，否则迟早漏一处。

**会话**单独建表，记录设备、IP、最近活动时间。用户在「安全」页能看到自己全部活跃会话并逐个下线；管理员暂停账号时批量吊销该用户的会话，但**不删 API Token**——鉴权时按账号状态拦截，解封即自动恢复，不用重新签发一遍。

### 7.2 相册管理

每个用户有自己的一组相册，可以增删改。相册本身的改名、可见性、排序与删除集中在一个「相册管理」页；图片的批量操作留在浏览页，两边互不掺杂。

**删除走回收站**：删图片、删相册都是先软删（相册连里面的图片一起），保留期内（默认 30 天，可配；填 0 关闭回收站）可以整份恢复；到期由后台清理任务彻底删除。回收站里的图片不占用户配额——引用计数已经归零，只是物理文件按保留期留着，这也是它占服务器空间的地方。管理员有一个"用户视图"开关：选择某个用户后，界面**只展示该用户的相册和图片**，管理员自己的相册完全不出现，避免混淆。退出该视图回到管理员自己的空间。

数据权限在服务端强制校验，不是靠前端隐藏。管理员跨用户访问会写审计日志。

### 7.3 图片浏览与选择

网格和列表两种视图，**两种视图都直接支持预览和多选**，不另设一个专门的"预览页"。用户在哪看就在哪操作，切来切去没有意义。

- **左键单击**：打开预览浮层看大图，支持左右切换、`Esc` 关闭、滚轮缩放。
- **Shift + 左键**：从上次点击位置到当前位置，按网格宽度范围连续选中多张。点第一张，按住 Shift 点同行的最后一张，整行就被选中。列表视图下同样的逻辑按行生效。
- **Ctrl + 左键**：离散多选。表头勾选框支持全选和半选状态。

选中后可以批量打标签、批量删除、批量移动到相册、批量复制直链。工具栏在有选中项时切换成批量操作条，显示已选张数。

### 7.4 支持的图片格式

在常见的 `jpg/jpeg/png/gif/webp` 基础上扩展到：

`bmp` · `tiff` · `avif` · `apng` · `ico` · `svg` · `heic/heif` · `jxl`

浏览器原生显示不了的（`heic`、`tiff`、部分 `jxl`），客户端在生成缩略图时用 WASM 解码（如 `libheif` 的 wasm 构建）转成 WebP 缩略图，原图照原样保存，下载时是原始格式。`svg` 单独处理：入库前剥离脚本与外部引用，直链响应头加 `Content-Security-Policy: sandbox` 和 `X-Content-Type-Options: nosniff`，或者对不可信来源的 SVG 强制 `Content-Disposition: attachment`。

格式白名单由后端配置驱动，管理员的"支持的图片类型"设置直接改这张表。

### 7.5 标签与广场

标签支持逐图添加、删除、下拉候选（输入时提示已有标签）、全局重命名、全局删除。

**广场**是公开图片流，按需求分两种状态：

- **未登录**：只能看到广场。顶部右上角一个登录按钮。可以按标签、关键词、上传时间搜索和筛选。
- **已登录**：广场页面上方是上传区，下方是广场内容。上传区和广场同屏，上传完直接能看到自己的图进了广场（如果设为公开）。

广场只展示 `visibility = public` 的图片，用户可以在上传或编辑时选择是否公开。管理员可以在「系统设置 → 首页展示相册」里只挑部分公开相册，选中后广场与自动漫游只取这些相册里的公开图片；不选表示沿用全部公开图片。搜索当前走 `title`、`original_name` 与标签名的 `LIKE` 匹配（大小写与转义由仓储层处理），没有依赖 PostgreSQL 专属的全文索引；数据量很大时再考虑加 GIN/`tsvector` 或外部搜索。

**背景音乐**：管理员可维护一份 Meting 主备 API 列表（平台 + 歌单 ID；第一条为主，失败或空歌单时按顺序尝试后面的），也可以使用服务器本地目录。Docker 部署的本地音乐路径由 `PIXORA_MUSIC_DIR` 指定容器内挂载点，后台输入会被覆盖。服务端把歌单归一化成统一结构并代理歌词；本地音频由 `/music/file` 带 Range 提供。前端在广场把圆形主图当唱片旋转，顶部按钮与侧栏控制播放/暂停，右侧抽屉在歌单与歌词间切换；侧栏底部有一张音量卡片，新访客默认音量由后台设置（初始 30%），可静音，音量同时作用在 Web Audio 增益与频谱律动上。播放时用 Web Audio 的频谱驱动圆片与光环律动。有声自动播放被浏览器拦截时，前端在第一次点击、触摸或按键后开始播放；滚轮、滚动和鼠标移动也会尝试解锁，但浏览器是否放行取决于它自己的策略。

### 7.6 API 与第三方客户端

对外只有这一套 v1 API：统一的信封结构、统一的错误码、统一的 Bearer 鉴权。
本项目是全新开发，不存在需要迁就的旧版调用方式，也不留「另一副面孔」的兼容端点。

端点总表：

| 方法 | 路径 | 作用 | 权限 |
|---|---|---|---|
| POST | `/api/v1/upload` | 上传单张图片，可指定相册 id 或 slug | upload |
| POST | `/api/v1/upload/batch` | 批量上传，多文件共用一套元数据 | upload |
| POST | `/api/v1/blobs/exists` | 批量预检哈希，判断哪些已存在 | upload |
| POST | `/api/v1/images/batch` | 批量删除 / 移动 / 打标签 / 改可见性 | write |
| GET | `/api/v1/images` | 图片列表，支持分页与标签筛选 | read |
| GET | `/api/v1/images/{id}` | 单张图片详情 | read |
| PATCH | `/api/v1/images/{id}` | 改标签、可见性、所属相册 | write |
| DELETE | `/api/v1/images/{id}` | 删除图片；引用归零后由 GC 回收物理文件（删除会立即催一次） | write |
| GET | `/api/v1/albums` | 相册列表 | read |
| POST | `/api/v1/albums` | 新建相册 | write |
| PATCH | `/api/v1/albums/{id}` | 改相册名称、可见性、排序 | write |
| DELETE | `/api/v1/albums/{id}` | 删除相册 | write |
| GET | `/api/v1/plaza` | 广场搜索，公开端点 | 公开 |
| GET | `/api/v1/random` | 随机一张/一批图：支持相册、集合、标签、方向/尺寸、时间窗口、count、seed、exclude_ids；带 Token 可看自己的私有库 | 公开 |
| GET | `/api/v1/music/playlist` | 背景音乐歌单（Meting API 或本地目录） | 公开 |
| GET | `/api/v1/music/lyrics` | 歌词文本；第三方歌词由服务端代理 | 公开 |
| GET | `/api/v1/music/file` | 本地音乐文件，支持 Range | 公开 |
| GET | `/api/v1/fs/tree` | 数据目录递归查询 | read |
| GET | `/api/v1/queue/{job_id}` | 查询队列任务状态 | read |
| GET | `/api/v1/me` | 当前用户信息与配额用量 | read |

`POST /api/v1/upload` 的字段：`file`（必填，也接受 `image` 别名）、`sha256`（可选，客户端算好的哈希；服务端仍会边收边算并与之对账）、`thumb`（可选，客户端生成的缩略图）、`album_id` 或 `album` / `album_slug`、`tags`、`visibility`、`original_name`、`reuse_existing`（可选，内容已在图库里就复用那一张）。管理员可带 `?uid=` 代目标用户上传，配额与相册归属都按对方算。

鉴权用 `Authorization: Bearer <token>` 或 `X-API-Key`。Token 在「API Token」页生成，库里只存哈希，可设权限范围（`upload` / `read` / `write` / `admin`）和过期时间；省略范围或传空数组时按 `upload + read` 处理。限流按用户的生效策略计数，同一用户的多个 Token 共享额度；Token 的 scopes 只决定能调哪些接口。每分钟额度在鉴权后强制，小时额度与 burst 目前只有配置字段，没有接入准入。

**错误码**统一用结构化 `error` 对象，客户端据此给不同提示，而不是只看 HTTP 状态码：

| code | HTTP | 含义 |
|---|---|---|
| `ACCOUNT_SUSPENDED` | 403 | 账号被暂停，可按 `appeal_url` 里的指引申请解封 |
| `ACCOUNT_BANNED` | 403 | 账号被封禁，需管理员解封 |
| `ACCOUNT_PENDING` | 403 | 邮箱未验证，账号未激活 |
| `IP_BLOCKED` | 403 | 来源 IP 命中黑名单 |
| `TOKEN_REVOKED` | 401 | Token 已撤销或过期 |
| `RATE_LIMITED` | 429 | 触发频率限制，带 `Retry-After` |
| `QUOTA_EXCEEDED` | 413 | 超出账号配额 |

暂停和封禁都返回 403，靠 `code` 区分。只给状态码的话，PicGo 这类客户端没法告诉用户到底是「可以申诉」还是「已封禁」，两种情况的提示文案完全不一样。

**PicGo / PicList 支持**：用「自定义 Web 图床」插件接标准 v1 API——上传地址填 `/api/v1/upload`，字段名 `file`，请求头带 `Authorization: Bearer <token>`，返回的 URL 从 `data.url` 取。文档里直接给可复制的 JSON 配置片段，用户填 Token 就能用。

### 7.7 数据目录递归查询

```
GET /api/v1/fs/tree?uid=1001&album=旅行&depth=3
```

返回该用户该相册下的目录树，包含每层的文件数、总大小、以及文件元数据。底层是数据库虚拟树（`users.uid → albums.slug → images`），文件系统上有硬链接镜像时两者一致，没有镜像时以数据库为准。

所有用户都能对自己的相册做增删改；管理员能对任意用户做。

### 7.8 存储后端管理

后台的存储管理页包含：默认存储类型切换、各后端配置、存储分布统计、存储类型启用状态、容量展示模式。

**物理存储方式**（本地目录还是数据库内，默认本地）可以在界面上切，但**存储路径不在界面上配**。容器部署时路径由环境变量注入，界面上只读展示来源和当前值，改路径要改 compose 文件再重启容器。放在界面上改路径有两个问题：一是容器里的挂载点改不了，改了也写不进去；二是配置文件一旦可写，就等于给了一个远程改服务器目录的入口，没必要冒这个风险。

这个选项和"元数据存储位置"是两回事。元数据可以在 PostgreSQL，图片实体可以在本地磁盘，两者独立配置。

远端后端（GitHub/WebDAV/Telegram）保留**失败自动回退本地**的行为，并在响应里带回 `fallback_message` 让前端提示用户。

### 7.9 统计与审计

存储管理页的统计面板保留：图片总数、总占用、各后端分布、按 MIME 类型分布、近 30 天上传趋势、今日分时上传、平均文件大小、最近上传记录。

新增用户维度的统计（各用户用量与配额占比）和审计日志（谁在什么时候删了什么、管理员跨用户访问记录）。

### 7.10 上传入口与队列

上传有四种入口，效果一样，进同一个队列：

- **拖拽**：文件或整个文件夹拖进虚线框，松开即入队。
- **选择文件**：系统文件选择器，支持多选。
- **选择文件夹**：递归扫描目录下的所有图片，相对路径保留成标签。
- **粘贴**：页面任意位置 `Ctrl+V`，截图工具截完直接贴。

上传框本身带预览，已入队的图片逐张显示缩略图，可单张移除，实时显示合计大小。预检结果单独提示（「8 张里有 3 张已存在，上传时自动跳过」）。

队列逐张上传，并发数默认 1，可在上传设置里调到 2 或 4。**队列状态存在浏览器本地（IndexedDB），刷新页面不丢**，这是长队列的刚需——1000 张传到一半误刷新，从头再来谁都受不了。

队列状态分四类，跳过单独算一类：成功、**跳过（服务器已有相同文件）**、等待中、失败。跳过没消耗带宽也没占盘，跟失败不是一回事，混在一起会让用户以为出了问题。

服务端另有一条持久化队列做背压：队列深度超过阈值时新请求直接返回 429 + `Retry-After`，客户端据此退避。

### 7.11 账号处置与解封

管理员可以对违规用户做两种处置，**两者都让网页登录和 API 同时失效**，区别在后续处理：

| 处置 | 效果 | 恢复方式 |
|---|---|---|
| 暂停使用 | 禁止登录与 API 调用，已上传内容保留但对外不可见 | 可申请解封，管理员审核后恢复 |
| 封禁 | 同上，另外隐藏全部公开内容，同邮箱与常用 IP 无法重新注册 | 需管理员手动解封 |

**处置确认框**里的字段：处置类型、生效时长（永久 / 7 天 / 30 天）、处置原因（会展示给用户，也写进邮件）、**解封要求**（多行可编辑，会填进邮件的「如何解封」部分）、申诉接收邮箱（默认取注册发信邮箱）、是否发送通知邮件。

确认后立即执行三件事：改账号状态、吊销该用户全部会话（踢下线）、写一条处置记录。API Token 不删，鉴权时按状态拦截，解封即恢复。

**通知邮件**由管理员邮箱发出，也就是注册时发验证码的那个账号。不额外配一个申诉邮箱，否则管理员要多看一个地方，容易漏。邮件正文取 `email_templates` 里的模板，包含暂停原因、内容保留说明、三步解封指引（准备材料 → 发送到管理员邮箱 → 邮件主题格式）和处理时限。暂停和封禁的文案必须分开：暂停写「可申请解封」并给材料清单，封禁只写「请联系管理员」，不承诺解封，否则会给出错误预期。

**三端表现**要一致：

- WEB：整页提示，不是弹个小窗。写清账号、暂停时间、原因，然后是解封指引，附申诉邮箱的复制按钮。
- API：403 + `code` + `reason` + `appeal_email` + `appeal_url`，客户端据此弹对应提示。
- 邮件：管理员点确认后自动发出。

### 7.12 服务条款

条款存在数据库里，管理员可在后台新增、修改、删除，改完即时生效，不用重启。

**版本化**是核心设计。每条条款有版本号、生效日期、更新摘要、正文和状态（草稿 / 生效中 / 已归档）。发布新版本时可以勾选「要求所有用户重新同意」，勾了用户下次登录会再弹一次通告，没勾就只是更新内容，不打扰用户。

**首次登录**强制弹出通告：遮罩不可点穿，没有关闭按钮，必须勾选「我已阅读并同意」才能继续。不同意的唯一出路是退出登录，但已上传的内容不会被删除。

弹窗有**三种形态**，共用同一份正文，切换只改容器尺寸，不重新加载内容，阅读位置保留：

| 形态 | 触发条件 | 表现 |
|---|---|---|
| 标准弹窗 | 视口 ≥ 768px | 居中，最大宽 580px，正文区高度取视口 55%，超出滚动 |
| 全屏阅读 | 点标题栏「全屏阅读」 | 铺满视口留 16px 边距，正文区吃满剩余高度，同意区固定底部 |
| 移动全屏 | 视口 < 768px | 自动铺满整屏，全屏按钮隐藏，按钮改纵向堆叠 |

之后用户在「用户中心 → 服务调整 → 服务条款」随时翻阅，能看到当前版本、更新摘要、正文、历史版本，以及**自己的同意记录**（什么时候同意的、来自哪个 IP）。

同意记录单独建表，只增不改。条款删除时记录不跟着消失，而且记录里冗余存一份版本号，日后追溯得到当初同意的到底是哪一版。生效中的版本不能直接删除，必须先把另一个版本设为生效。

### 7.13 配额与容量

系统总额有两个来源，管理员选：

- **自动探测**：读 `statfs` 拿真实磁盘容量，本地盘和云盘用这个。
- **手动配置**：管理员手填总额，用于 OSS 之类的网络挂载。

为什么需要手动这一项：数据目录挂在 ossfs 上时，`statfs` 返回的是挂载伪值（常见是 16 EB），跟真实可用空间毫无关系。所以检测到网络文件系统挂载就自动降级，提示管理员手填。

**已用分两个口径**（详见 6.5）：自动模式下占用率按**宿主机整盘已用**算（总额 − 可用），磁盘被任何东西写满都得知道；手填总额与网络挂载降级时拿不到可信的整盘数字，退回**本项目占用**（已存文件实时汇总），因为手填的数可能只是给本项目定的预算。两个数字在页面上分开摆，不合成一个。

**配额总额是硬约束**：所有已注册用户的配额合计 + 管理员账户配额 ≤ 可分配上限，上限 = 系统总额 − 系统占用（宿主机整盘已用）——磁盘上别的数据先占住的额度分不出去，不扣掉就会出现「配额都发完了、上传却写不进盘」；手填总额或网络挂载降级时拿不到整盘数字，上限就是总额。改任何一个人的配额都要先算一遍，超额时拒绝保存并提示还差多少。不拦的话，管理员随手给几个人加到几百 GB，上限早就超了也不知道。已经越界时（磁盘占用会把上限压低）只拦往上加、调低放行，否则管理员连回到合规状态都做不到。

**注册默认配额**和**单用户配额上限**单独配置，注册时自动套用默认值。剩余可分配不足时，新用户拿剩余额度并提示管理员。

**容量触顶自动关闭注册**：占用超过阈值（默认 90%）时自动停掉注册入口，降到恢复阈值（默认 80%）以下自动重开；占用率按上面说的口径取（自动模式下是宿主机整盘）。已注册用户完全不受影响，照常上传。注册页在关闭时整页替换成提示，说明是哪条线（宿主机磁盘 / 本项目）触顶、已注册用户不受影响、什么时候可能恢复，而不是只把按钮灰掉。

普通用户在任何界面看到的都是「已用 / 管理员分配的配额」，跟真实磁盘容量无关。

### 7.14 频率限制与 IP 黑名单

**频率限制**分两层：全局默认 + 用户级覆盖。改全局默认时，标了「继承默认」的用户立刻跟着变，标了「自定义」的不受影响。管理员默认豁免。

API 调用和图片上传**分成两套额度**，因为成本差得远——一次列表查询和一次 20MB 上传对磁盘的影响不是一个量级，共用一个桶会互相挤占。具体项：

- API：次/分钟、读接口单独限额。小时额度与 burst 字段已经进策略表，但当前只强制每分钟额度；管理页会展示这些值，部署时不要把“配了小时额度”当成已经生效。
- 上传：张/分钟、张/小时、张/天、单日上传流量。
- 并发与批次：单用户并发上传数、单批次最大张数、单文件大小上限、队列深度阈值。

**API 限流在鉴权之后执行。** 读接口用 `api_read_per_minute`，写接口用 `api_per_minute`，管理员豁免；浏览器会话只过进程内令牌桶，Token 客户端与写操作才落库计数，避免把每次看图变成两次写。`api_per_hour` 与 `api_burst` 目前没有接入准入逻辑，这一点在接口契约和审计报告里都标了，别把它当成已有的保护。

**上传策略也能按用户设置**：单文件上限、单批张数、像素上限、格式白名单四项走同一张覆盖表，取值链是**单用户覆盖 → 全局默认 → 系统设置里的站点默认**，`0` 与空格式串表示「跟随上一层」。这四项必须真的生效，而不是只挂在界面上：单文件上限在收 multipart 流的截断阈值上生效（超限的字节根本不落盘），像素上限与格式白名单在上传校验里判，单批张数与并发数由 `/me` 的 `limits` 下发给客户端队列——客户端据此限流，否则「按用户收紧」只是一句空话。写成 `0` 跟随的人，管理员改系统设置时会立刻跟着变；标了自定义的不受影响。

**上传限额按实际落盘的新文件计数**，被去重跳过的文件不占额度。这条是跟内容寻址存储的设计咬合的：重复文件本来就没写盘，也不该消耗上传配额，否则用户批量传重复图会被莫名其妙限流。

超限处理：返回 429 + `Retry-After`（默认）、写审计日志并可邮件通知管理员、连续超限 N 次自动临时封禁 M 分钟。**临时封禁只针对 API，不影响该用户网页登录**，它和账号暂停是两回事，界面上要标清楚，别让管理员混用。

计数实现要提前定：单实例用进程内令牌桶加滑动窗口，够快也够省内存。多实例部署时计数必须共享，走数据库计数表或可选接 Redis，否则每个实例各算各的，实际额度会被放大成 N 倍。当前实现是单实例口径：进程内限流、进程内会话活动节流、进程内 blob 锁，多实例下都需要额外的共享设施。

**IP 黑名单**支持单个 IP 和 CIDR 网段（IPv4 与 IPv6），拦截范围可选全站 / 仅注册 / 仅登录 / 仅上传，带备注、命中次数统计和到期时间。`scope=all` 的规则由全站中间件执行，浏览广场、拉直链也会被拦；注册/登录/上传各自再按场景检查一次。策略区包含是否信任反向代理头、可信代理层数（只信最靠近服务端的一层，防止客户端伪造 `X-Forwarded-For` 绕过）、以及自动临时封禁的阈值与时长。环境变量 `PIXORA_TRUST_PROXY` 是后台设置没写过时的默认层数，保存过后台策略后以数据库为准；两边别配成互相矛盾的值。规则命中次数按每分钟一次节流，被拦客户端反复重试不会把封禁变成写放大。规则表区分手动规则和风控自动加的临时规则，后者可以提前解除。

另配一份**白名单**：管理员自己的固定 IP 或公司出口 IP 加白后，即使被自动风控误伤也能进去处理。白名单与黑名单冲突时白名单优先。

### 7.15 多端与响应式

全站一套代码适配 PC 和移动端，五个断点，移动优先，统一用 `min-width` 往上增强：

| 代号 | 宽度 | 布局策略 |
|---|---|---|
| XS | < 480px | 单列，底部 tab，卡片内边距收紧到 10px |
| SM | 480–767px | 单列，底部 tab，网格可放两列 |
| MD | 768–1023px | 两到三列，侧边栏可折叠，表格转精简列 |
| LG | 1024–1439px | 三到四列，侧边栏常驻，内容区限宽 1200px |
| XL | ≥ 1440px | 五列，内容区限宽 1400px 居中 |

断点就这五个，不再往下切。真正决定体验的不是断点数量，是几条具体规则：

**表格什么时候转卡片。** `< 768px` 转卡片列表；`768–1023px` 隐藏次要列（尺寸、哈希、注册时间），保留名称、标签、大小、操作。

**多选怎么换。** PC 是 `Shift + 左键`按网格范围连选、`Ctrl` 离散多选；移动端没有 Shift 键，改成**长按进入多选模式**，之后逐张点选，另给一个「全选本页」。

**上传入口怎么换。** 触屏拖不了文件，移动端换成「从相册」「拍照」「从文件」三个入口。剪贴板里的图片走「从相册」入口——iOS 和 Android 都会把刚截的图排在相册最前面，这是系统行为，比自己做一个粘贴按钮更顺手。

**图片预览用系统手势。** 移动端全屏，左右滑切换、双指缩放、下拉关闭，不再依赖键盘的 `←` `→` 和 `Esc`。

**导航降级。** PC 的左侧侧边栏，移动端收成底部 4 个 tab（广场 / 相册 / 上传 / 我的），其余入口进「我的」页的纵向列表。管理后台的侧边栏收进汉堡抽屉。

两个容易漏的细节：底部 tab 和批量操作条要加 `env(safe-area-inset-bottom)`，否则全面屏上会被手势条挡住；移动端输入框高度 ≥ 40px、按钮 ≥ 44px、图标点击区 ≥ 44×44px，不然手指点不准。字号本身不随断点缩放，只调间距和触控区。

还有一个 64 位哈希的坑：长串不加 `overflow-wrap:anywhere` 会把布局撑破，直接顶出横向滚动条。

## 8. 安全设计

| 面 | 措施 |
|---|---|
| 密码 | Argon2id，加盐；哈希与校验放在受限的 `spawn_blocking` 里，容器里同时最多跑两份 |
| 会话 | HttpOnly + SameSite=Lax + Secure Cookie；API 用签名 Token；会话独立建表可逐个吊销；活动时间按分钟节流 |
| CSRF | 双提交 Cookie 或同步 Token，所有写操作校验 |
| OAuth | `state` 用主密钥签名，同时把哈希写进 HttpOnly Cookie；回调必须签名、provider、浏览器三者一致 |
| 账号状态 | 鉴权中间件统一校验 `active`，暂停与封禁的账号在 WEB 与 API 两侧同时失效 |
| 上传校验 | 魔数嗅探真实 MIME、大小上限、像素与长宽上限、缩略图像素上限、扩展名白名单 |
| 路径穿越 | 所有存储 key 由服务端生成（哈希）；本地驱动拒绝 `..`、绝对路径与 Windows 盘符 |
| SVG | 入库前净化（含命名空间前缀），响应再加沙箱 CSP |
| 前端输出 | 弹窗/确认框字符串按纯文本渲染，只保留 `<br>`；用户可控名称不拼进 `innerHTML` |
| 凭据加密 | AES-256-GCM，主密钥走环境变量/密钥文件 |
| 隔离 | 每次读写校验资源归属；管理员越权访问记审计 |
| 限流 | IP + 用户 + Token 三维度；验证码发送、上传、API 各自独立额度；API 当前强制每分钟额度 |
| IP 控制 | 黑名单支持 CIDR 与分场景拦截；全站规则在中间件执行；白名单优先，命中计数节流 |
| 直链 | 哈希命名不可枚举；公开/私有分缓存；SVG 沙箱；可选防盗链 Referer 白名单 |
| 响应头 | `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy`、`frame-ancestors 'self'` |
| 配置面 | 存储路径等敏感配置只走环境变量，不在界面开放写入 |
| 依赖 | 最小依赖，定期扫描漏洞 |

三条容易被绕过的点，写进代码评审清单：

`blobs` 的删除必须严格走引用计数。任何绕过计数直接删物理文件的代码路径都是隐患，因为同一份文件可能被多个用户引用。上传去重与 GC 现在共用按内容哈希分片的进程内锁，但多实例仍需要数据库级锁或只让一个实例跑 GC。

账号状态的校验必须在鉴权中间件里做，不能散落到各个 handler。漏一处就等于给暂停的账号留了一个后门。

限流计数在多实例部署下必须共享。各实例独立计数的话，实际额度会被放大成实例数的倍数，限流形同虚设。

2026-10-17 的审计确认并修复了上传 SVG 未净化、OAuth state 未绑定浏览器、确认弹窗存储型 XSS、API 限流未接线、全站 IP 规则不覆盖浏览/直链、关闭广场后 `/random` 仍匿名可用等问题；设置读取缓存、会话活动时间节流、随机图快路径也在同一次里落地。未修复项、部署侧需要确认的边界和完整上线检查清单见 [`docs/安全与性能审计-2026-10-17.md`](安全与性能审计-2026-10-17.md)。

## 9. 部署方案

### 9.1 Docker Compose

```yaml
services:
  pixora:
    image: pixora:latest
    environment:
      PIXORA_DB_DRIVER: postgres
      PIXORA_DB_DSN: postgres://pixora:***@db:5432/pixora
      PIXORA_DATA_DIR: /data
      PIXORA_MASTER_KEY: ${MASTER_KEY}
      PIXORA_WORKERS: "4"
      RUST_LOG: info
    volumes:
      - ./data:/data
    deploy:
      resources:
        limits: { memory: 128M }
    depends_on: [db]

  db:
    image: postgres:16-alpine
    command: >
      postgres -c shared_buffers=64MB -c work_mem=4MB
               -c max_connections=50 -c effective_cache_size=128MB
    volumes:
      - ./pgdata:/var/lib/postgresql/data
    deploy:
      resources:
        limits: { memory: 200M }

  caddy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - ./data:/srv/data:ro
    deploy:
      resources:
        limits: { memory: 48M }
```

三个服务的内存上限加起来 376M，给系统留了余量。

应用镜像用多阶段构建：构建阶段用 `rust:1.98` 装 musl 目标并编译，运行阶段用 `scratch`，只放一个静态链接的二进制、CA 证书和时区数据。最终镜像在 20MB 上下，冷启动毫秒级。

```dockerfile
FROM rust:1.98 AS build
# 架构按构建机自身决定：buildx 多平台构建时它已经在目标架构上了
RUN set -eu;     case "$(uname -m)" in       x86_64)  MUSL=x86_64-unknown-linux-musl ;;       aarch64) MUSL=aarch64-unknown-linux-musl ;;     esac;     echo "$MUSL" > /tmp/musl-target;     rustup target add "$MUSL"
WORKDIR /src
COPY . .
RUN cargo build --release --target "$(cat /tmp/musl-target)"

FROM scratch
COPY --from=build /src/target/*/release/pixora /pixora
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
ENV TZ=Asia/Shanghai
ENTRYPOINT ["/pixora"]
```

跨平台编译交给 Docker 就行，本机不需要装 musl 目标——本地开发用 msvc 目标跑 `cargo run`，出镜像时才进容器编 musl。多架构镜像交给 GitHub Actions 的 `docker.yml`：`docker buildx build --platform linux/amd64,linux/arm64` 一条命令出两份，arm64 那趟靠 QEMU 模拟，慢但一次性。

### 9.2 环境准备

开发环境需要 Rust 工具链（stable）、PostgreSQL 或 MariaDB、Node.js。Rust 的 `RUSTUP_HOME` 与 `CARGO_HOME` 建议指向项目自带的工具链目录，避免和系统里其它版本混在一起。本地开发直接 `cargo run` 即可；出 Linux 镜像时进 Docker 编 musl 目标，不需要在本机装交叉编译工具链。

开发与测试产物统一放在项目目录下。`target/` 目录体积很大，用完不需要保留时直接删除，临时文件不进回收站。

如果后续需要补装运行时（比如 Docker Desktop 或某个数据库版本），统一装到项目所在的盘，不污染系统盘。

### 9.3 环境变量

存储路径这类配置只走环境变量，不在界面开放写入。界面上只读展示来源和当前值。

| 变量 | 默认 | 说明 |
|---|---|---|
| `PIXORA_DB_DRIVER` | `sqlite` | `sqlite` / `postgres` / `mysql` |
| `PIXORA_DB_DSN` | 数据目录里的 `pixora.db` | 连接串，SQLite 时填文件路径 |
| `PIXORA_DATA_DIR` | `./data` | 数据目录，容器里是挂载点 |
| `PIXORA_MASTER_KEY` | 首次启动自动生成到数据目录 | 加密主密钥，用于存储后端凭据与 SMTP 密码 |
| `PIXORA_WORKERS` | 等于 CPU 核数 | 队列 worker 数 |
| `PIXORA_BIND` | `0.0.0.0:8080` | 监听地址 |
| `PIXORA_BASE_URL` | 自动探测 | 生成直链用的基础地址，反代场景必须显式设置 |
| `PIXORA_TRUST_PROXY` | `1` | 可信代理层数；后台 IP 策略没写过时用这个值，保存过后台策略以数据库为准 |
| `PIXORA_COOKIE_SAMESITE` | `lax` | 会话 Cookie 的 SameSite：`lax` 或 `strict` |
| `PIXORA_SECURE_COOKIES` | 按 `BASE_URL` 是否 https | HTTPS 下应为 true；本地 http 调试可以显式设 false |
| `PIXORA_DB_MAX_CONNECTIONS` | SQLite 4 / 其它 10 | 连接池上限 |
| `PIXORA_ACCEL_PREFIX` | 空 | `X-Accel-Redirect` 前缀，让 Nginx 直接发文件 |
| `PIXORA_WEB_DIR` | 空 | 指向前端产物目录则读盘而不是读嵌入资源（开发用） |
| `PIXORA_DEV_RETURN_CODES` | 关 | 把邮箱验证码放进响应里（仅本机开发） |
| `PIXORA_HTTP_PROXY` | 空 | 出网代理覆盖项，用于 OAuth、存储后端等；不填时 Windows 自动读「Internet 选项」里的系统代理，其它平台跟随 `HTTPS_PROXY` / `ALL_PROXY` |
| `RUST_LOG` | `info` | 日志级别 |

完整清单与示例见 `deploy/.env.example`。

两个容易踩的点。`PIXORA_BASE_URL` 在反向代理后面必须显式设置，否则自动探测出来的是容器内部地址，直链、邮件链接和 OAuth 回调都会错。`PIXORA_TRUST_PROXY` 只信最靠近服务端的那一层：设大了，客户端可以自己伪造 `X-Forwarded-For` 绕过 IP 黑名单和限流；设小了，反向代理后面的所有请求会被记成同一个代理 IP。

### 9.4 首次启动

首次启动跑一个交互式安装向导：管理员账号、站点域名、邮件 SMTP、默认存储方式。数据库那一步是连接自检，不是配置；实际的库由 `PIXORA_DB_DRIVER` / `PIXORA_DB_DSN` 在启动时决定，改完环境变量并重启才会切换。校验通过后写配置、建表、创建管理员，然后锁定安装入口。

存储路径不在向导里填，由 `PIXORA_DATA_DIR` 注入。本地直接跑时默认取当前目录下的 `./data`。

### 9.5 自动化

`.github/workflows/` 下两个工作流：CI（类型检查 + 测试 + 端到端冒烟 + Windows 编译检查）、发行版与镜像（按版本号发 Release、出 Linux/Windows 可执行文件、推容器镜像）。推送标签即发版，不需要手工打包。

响应式不要留到最后补。M4 做相册页的时候就把断点和「表格转卡片」的规则定下来，后面每个页面照着写。等到 M7 再回头改，等于把每个页面重做一遍。

## 11. 风险与取舍

**客户端缩略图依赖浏览器能力。** HEIC 这类格式在部分浏览器里没有原生解码，需要引入 WASM 解码器，体积不小（几百 KB）。缓解方式是按需加载——只在用户真的选了这类文件时才下载解码器。

**硬链接在对象存储挂载上不可用。** 已经设计了降级路径（虚拟目录树），但意味着在那种环境下磁盘上不会有直观的 `用户/相册` 目录。如果管理员依赖文件系统直接浏览，需要提前说明。

**邮件送达率。** 自建 SMTP 发验证码容易进垃圾箱。用阿里云企业邮箱能改善，但仍建议配置 SPF/DKIM/DMARC。方案里给邮件发送加失败重试和备用通道配置。

**Rust 的编译时间是真实的摩擦。** 全量编译几分钟，改了底层 crate 会触发大范围重编。缓解手段是把 workspace 拆细（见附录 C），让改动尽量限制在单个 crate 内，同时在 CI 里挂 `sccache` 缓存。本地用 `cargo check` 代替 `cargo build` 做快速验证。

**异步 Rust 的学习曲线不低。** 生命周期、`Send`/`Sync` 约束、`Pin` 这些概念会在写并发存储驱动时集中冒出来。建议一开始就把 `StorageDriver` 的 trait 边界设计对（全部 `Send + Sync`，参数用 `Box<dyn AsyncRead + Send + Unpin>`），避免后期大面积返工。

**PostgreSQL 内存调参有下限。** 压到 96MB 常驻是可行的，但连接数一多还是会涨。如果发现吃紧，切 SQLite 是直接的出路。

**OSS 挂载下容量探测只能靠人工。** `statfs` 在 ossfs 上返回 16 EB 这种伪值，没法从文件系统推断真实容量。方案里改成管理员手填总额、已用量由数据库汇总，代价是总额要靠人维护。如果管理员忘了更新，配额校验的基准就是错的。缓解办法是在存储管理页常驻一条提示，标明当前总额是手填的以及填的时间。

**配额总额校验有并发窗口。** 两个管理员同时给不同用户加配额，各自算的时候都没超，提交完就超了。要在这个校验上加行级锁或者用一个串行的配置版本号，不能只靠"读一次、算一下、写回去"。

**多实例部署会同时打破限流、会话吊销和 GC。** 限流计数不共享，额度被放大；会话吊销只在本实例生效，其他实例上的旧会话还活着；上传去重与 GC 的分片锁只在进程内，两个实例可能同时回收同一实体。如果确实要多实例，这几项都得先接上共享存储（数据库计数表、会话表轮询、数据库 advisory lock 或单独一个 GC 实例），或者干脆保持单实例。单实例配合垂直扩展，在这个项目的规模下够用很久。

**服务条款目前靠前端提示。** 登录后弹通告、记录同意，但通用鉴权没有强制拦截，API Token 可以绕过；注册流程也没有落一条同意记录。条款有法律约束力时，需要在服务端补 `TERMS_REQUIRED` 逻辑，或至少在注册接口里带上同意标记。

**一切取舍都写进 ADR。** 语言选 Rust、架构选模块化单体、去重用 CAS + 引用计数、缩略图放客户端、路径走环境变量、服务条款版本化——这些决策都值得留档，将来有人问"为什么不用 Go / 为什么不用微服务 / 为什么路径不给改"时能翻出来看。附录 D 收了六条已经定下来的 ADR。

## 附录 D：已定决策 ADR

### ADR-0001：运行时选择 Rust

**状态**：已接受

**背景**：Docker 整栈内存上限 500MB，常驻越低越好；性能要求极致；开发周期不计入考量。

**决策**：使用 Rust（axum + tokio），静态链接 musl 目标，分配器换 mimalloc。

**备选方案**：Go 1.23。空载内存 10–20MB、峰值可达 Rust 的两三倍，且 GC 在高负载下引入毫秒级尾延迟。开发效率更高，但工期不是本项目的约束条件，所以不采纳。Java 因 JVM 基线内存直接出局，Python 和 Node.js 因并发模型与内存表现出局。

**影响**：正面是内存和尾延迟最优、二进制可跑在 scratch 镜像上。负面是编译慢、异步心智负担高、生态相对少一档，需要靠拆细 workspace 和 `sccache` 缓解。

### ADR-0002：架构风格选择模块化单体

**状态**：已接受

**背景**：需要高吞吐、低资源占用、单机可部署；团队规模小，运维能力有限。

**决策**：模块化单体，内部四层，存储后端用微内核插件模式，API 与后台 Worker 同进程。

**备选方案**：微服务。可伸缩性和演进性最强，但资源开销与运维复杂度最高，在 500MB 预算下自相矛盾。基于服务的架构可以拆出独立 worker，但多一个进程就多一份内存和一套部署逻辑，收益不划算。

**影响**：正面是内存占用低、部署简单、单进程内调用无网络开销。负面是模块边界靠代码纪律维持，长期有腐化成"大泥球"的风险，需要靠 crate 划分和接口约束来守住边界。

### ADR-0003：物理存储路径走环境变量，不在界面开放

**状态**：已接受

**背景**：早期设计把数据目录放在后台设置页里配置。容器部署下这个做法行不通，容器内的挂载点是编排文件决定的，界面改了也写不进去。

**决策**：数据目录由 `PIXORA_DATA_DIR` 注入，界面上只读展示来源和当前值。物理存储**方式**（本地目录还是数据库内）仍可在界面切换，因为它不涉及文件系统路径。

**备选方案**：保留界面配置，容器里把路径挂成可写。风险是把一个远程改服务器目录的入口暴露在 Web 层，一旦后台账号失守，攻击面直接扩大到文件系统。不值得。

**影响**：正面是配置面收窄，容器行为可预期。负面是改路径要改编排文件并重启容器，非技术管理员做不了这件事，需要运维配合。

### ADR-0004：服务条款版本化，同意记录独立留存

**状态**：已接受

**背景**：条款会被修改。如果只存一份最新版，用户事后无从知道自己当初同意的是什么，管理上也没有凭据。

**决策**：条款按版本存库，每条有版本号、生效日期、更新摘要、正文和状态（草稿 / 生效中 / 已归档）。同意记录单独建表，记录用户、版本、时间和 IP，只增不改。记录里冗余存一份版本号，条款删除也不影响追溯。

**备选方案**：只存最新版，同意与否记一个布尔值在 users 表上。实现最省事，但没有任何追溯能力，出问题的时候说不清。

**影响**：正面是合规上站得住，用户能回看历史版本。负面是数据量随版本增长，条款表和同意表都要长期保留，不能随用户删除一起清理。

### ADR-0005：频率限制采用全局默认 + 用户级覆盖两层

**状态**：已接受

**背景**：需要限制 API 调用和上传频率，但不可能给每个用户单独配一遍。

**决策**：`rate_limit_policies` 表里 `user_id` 为空的那一行是全局默认，其余是用户级覆盖。改默认值时继承的用户立刻跟着变，自定义的不受影响。管理员默认豁免。API 与上传分两套额度，上传按实际落盘的新文件计数，去重跳过的文件不占额度。

**备选方案**：按用户组配置。灵活但多一层间接，这个规模的项目用不上，用户数上百之后再考虑加分组。

**影响**：正面是配置成本低，改一处影响一批。负面是"这个用户到底受什么限制"要跨两行数据判断，界面上必须把「继承默认」和「自定义」标清楚，否则管理员会搞混。

### ADR-0006：账号处置区分暂停与封禁，解封走邮件人工审核

**状态**：已接受

**背景**：需要一个既能让违规用户停手、又给误伤用户留出路的机制。

**决策**：分两种处置。暂停是临时的、可申请解封；封禁更重，会隐藏公开内容并阻断同邮箱重新注册，需管理员手动解封。两者都让 WEB 与 API 同时失效。管理员点确认后由注册发信邮箱自动发出通知邮件，正文里写明解封要求。解封要求做成可编辑模板，不同违规类型可以给不同材料清单。

**备选方案**：做站内申诉表单。体验更好，但要额外做申诉列表、状态流转、附件上传，还得防刷。用邮件人工处理在当前规模下成本更低，而且申诉量本来就少。

**影响**：正面是实现简单、处置留痕清晰。负面是申诉走人工，管理员要盯邮箱，量大之后会成为瓶颈。真到那一步再加站内申诉也不迟，邮件通道可以并行保留。
